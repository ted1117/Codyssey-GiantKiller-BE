# PRD-005: 보안 사건 관리

## 1. 배경

- 현재 문제: 통화의 분석 진행·결과와 알림·앱 설치에서 발생한 위험을 기록하지 않으면 가족이 사건의 진행 상태를 확인할 수 없다.
- 왜 지금 필요한가: 자녀 웹 대시보드와 통화 간 연관성 판단을 위한 공통 데이터 저장소가 필요하다.
- 관련 문서/이슈: 「부모 지킴이 상세 기획서」 4·6·12장

## 2. 목표

- 사용자가 무엇을 할 수 있어야 하는가: 자녀가 본인 가족의 위험 사건과 요약·지시·대응 상태를 조회한다.
- 비즈니스 또는 운영상 기대 효과: 단발성 경고가 아닌 연속 사건의 흐름을 확인할 수 있다.

## 3. 대상 사용자

- 주요 사용자: 자녀
- 보조 사용자: 부모님, 자녀 웹, AI 분석·위험 대응 서비스
- 관리자 또는 운영자 영향: 사건 발생·분석 실패를 추적할 수 있다.

## 4. 범위

이번 작업에 포함:

- [ ] 알림·통화·앱 설치 사건 공통 저장
- [ ] 위험 여부와 관계없이 정상적으로 접수한 모든 통화를 사건으로 저장
- [ ] AI 위험 분류·요약·지시 및 분석 상태 관리
- [ ] 분석 결과가 위험·의심인 통화 사건에 한정한 자녀 알림
- [x] 가족별 사건 목록·상세 조회, 아래 승인된 최소 공개 범위 적용
- [x] 자녀의 명시적 선택에 따른 사건 대응 상태 갱신

이번 작업에 포함하지 않음:

- [ ] 통화 원본을 자녀에게 공개
- [ ] 고급 통계·주간 리포트·관리자 분석 화면
- [ ] 통화 업로드 멱등성 보장·중복 이벤트 방지, 재분석, 자동 재시도 (후속 TODO)

## 5. 사용자 흐름

1. Android가 전송한 통화의 입력·권한 검증이 완료되면 백엔드가 AI 분석 전에 사건을 저장한다.
2. 백엔드가 AI 분석 결과를 검증해 해당 사건의 분석 상태·분류·요약·지시를 갱신한다. 분석 실패도 같은 사건에 남긴다.
3. 정상으로 분석된 통화는 사건을 유지하되 대응 불필요로 처리하고 자녀에게 알리지 않는다. 위험·의심으로 분석된 통화 사건만 자녀에게 알린다.
4. 자녀가 웹에서 가족의 사건 목록과 상세 요약·위험 지시를 조회하고 대응 상태를 갱신한다.

위 흐름은 통화 사건에 적용한다. 알림·앱 설치 사건의 생성 시점과 기준은 별도로 정한다.

## 6. 기능 요구사항

- FR-1: `SecurityEvent`에 가족·유형·위험 수준·상태·발생 시각을 기록한다.
- FR-2: 통화에서 추출한 `CallInstruction`을 사건과 연결해 저장한다.
- FR-3: `GET /api/v1/events`, `GET /api/v1/events/{id}`로 가족별 기록을 제공한다.
- FR-4: 사건 확인/완료 상태를 갱신한다.
- FR-5: 모든 통화 사건에 분석 진행·완료·실패 상태를 기록한다.
- FR-6: 검증된 분석 결과가 위험·의심인 통화 사건만 자녀 알림 대상으로 삼는다. 정상 결과나 분석 대기·진행·실패만으로 자녀에게 위험 알림을 보내지 않는다.

### 6.0. 자녀 조회 1차 승인 범위 (2026-10-31)

- 해당 가족의 `CHILD`만 목록·상세를 조회한다. 대표 여부는 제한하지 않는다.
- 공개 대상은 `COMPLETED`이면서 `requires_attention=true`인 `CALL`과 `CHILD_IMPERSONATION`으로 분류된 `ALERT`다. 기존 사칭 문자의 분석 상태·판정값은 NULL일 수 있다.
- 정상·분석 대기·진행·실패 통화는 목록과 상세 모두 숨긴다. 숨긴 사건은 ID로 요청해도 404를 반환한다.
- 목록·상세 모두 `id`, `summary`, `analysis_status`, `status`, `occurred_at`만 반환한다. 위 FR-3·수용 기준의 유형·위험도·지시 공개는 이번 조회 범위에서 제외한다.
- `GET /api/v1/events?family_id={UUID}&limit=20&offset=0`은 발생 시각 최신순이다. 같은 시각에는 저장 시각·ID 내림차순으로 정렬한다. limit은 1~100, 기본 20이며 offset은 0 이상이다.
- `GET /api/v1/events/{event_id}`는 동일한 공개 조건·자녀 권한을 적용한다. 상세 조회만으로 대응 상태를 변경하지 않는다.
- 사건 대응 변경·오늘 요약·통화 지시·가족 확인 상세 공개는 이번 범위에 포함하지 않는다. DB 모델·마이그레이션은 변경하지 않는다.

### 6.0.1. 자녀 대응 상태 변경 추가 승인 (2026-10-31)

- 사용자 추가 승인으로 대응 상태 변경을 구현한다. 조회 1차의 대응 변경 제외 범위보다 이 절을 우선한다.
- `PATCH /api/v1/events/{event_id}/status`에 `status: ACKNOWLEDGED | RESOLVED`를 전달한다. 응답은 조회와 같은 최소 5개 필드다.
- 공개 사건에 대해 해당 가족의 모든 CHILD가 변경할 수 있다. 부모·타 가족은 403, 없는 사건·숨긴 사건은 404다.
- `OPEN → ACKNOWLEDGED`, `OPEN → RESOLVED`, `ACKNOWLEDGED → RESOLVED`를 허용한다. 같은 상태의 재요청은 200, `RESOLVED → ACKNOWLEDGED`와 그 밖의 전이 충돌은 409다.
- 입력의 OPEN·NOT_REQUIRED·다른 값·추가 필드는 422다. DB 사건 행 잠금으로 동시 변경을 직렬화한다.
- 분석 결과·분석 상태·가족 확인 결과를 변경하거나 알림을 발송하지 않는다. 해결은 가족의 대응 완료 표시이며 안전 보증이 아니다.

### 6.0.2. 자녀 조회 공개 필드 확대 승인 (2026-10-31)

- 사용자 승인으로 6.0의 5개 필드 제한을 이 절이 대체한다. 공개 조건·권한·정렬·페이지 처리는 변경하지 않는다.
- 목록·상세·`PATCH /api/v1/events/{event_id}/status` 응답은 `id`, `event_type`, `classification`, `risk_level`, `summary`, `analysis_status`, `status`, `occurred_at` 8개 필드를 반환한다. `classification`·`risk_level`이 NULL이면 `null`로 반환하며 보정하지 않는다.
- 상세(`GET /api/v1/events/{event_id}`)만 `instructions: [{"instruction_type": str}]`를 추가로 반환한다. 지시가 없으면(예: `ALERT`) 빈 목록이다. 목록과 PATCH 응답에는 `instructions`를 포함하지 않는다.
- `CallInstruction.description`은 통화 내용이 포함될 수 있어 어떤 응답에도 공개하지 않는다.
- 가족 확인 결과는 계속 공개하지 않는다. `risk_score`는 컬럼이 없어 제공하지 않는다. DB 모델·마이그레이션은 변경하지 않는다.

### 6.0.3. 위험 문자 사건 공개 추가 (2026-10-31)

- 사용자 승인으로 자녀 조회 공개 조건에 세 번째 분기를 추가한다: `event_type=ALERT`이고 `requires_attention`이 true인 사건. 분류가 `CHILD_IMPERSONATION`이 아닌 위험 문자(PRD-002 5.2)가 대상이다.
- 기존 두 분기(분석 완료·주의 필요 통화, 사칭 문자)는 변경하지 않는다. `requires_attention`이 false 또는 NULL인 사칭 이외 `ALERT`는 계속 숨긴다. 응답 필드·권한·정렬은 6.0.2와 같다.

### 6.1. 통화 사건의 정의와 생성 기준

- 통화 한 건을 사건 하나로 다룬다. 사건은 통화의 분석·대응을 추적하는 기록이며, 사건의 존재 자체가 위험 또는 사기 확정을 뜻하지 않는다.
- 입력·권한 검증을 통과해 정상적으로 접수한 모든 통화를 위험 여부와 관계없이 저장한다. 정상으로 분석된 통화도 사건을 유지한다.
- 사건 생성·갱신은 백엔드가 담당한다. Android는 통화 데이터를 전송하고, AI는 분석 결과를 반환한다.
- AI 분석 전에 사건을 저장하고, 분석 결과와 분석 상태를 같은 사건에 기록한다. 분석 상태는 가족의 대응 상태와 구분한다.
- AI 호출 실패 또는 결과 스키마 검증 실패는 분석 실패로 남기며, 정상·안전 판정으로 대체하지 않는다.
- 서로 다른 통화는 별도 사건으로 유지한다. 해커톤 최소 구현에서는 접수 요청 단위로 사건을 생성하며, 같은 통화의 재전송에 대한 중복 방지는 보장하지 않는다. 멱등성 키와 재분석 기능은 후속 TODO로 둔다.
- 모든 통화 사건의 저장이 원본 녹음의 계속 보관을 의미하지는 않는다. 원본 보존 정책은 별도로 정한다.

### 6.2. 분석 상태·대응 상태와 자녀 알림

- 분석 상태는 `PENDING`(접수·대기), `PROCESSING`(분석 중), `COMPLETED`(분석 완료), `FAILED`(분석 실패)로 구분한다. 분석 완료는 안전 판정이 아니며 정상·위험 여부는 분석 결과로 표현한다.
- 대응 상태는 `OPEN`(미확인), `ACKNOWLEDGED`(자녀가 확인), `RESOLVED`(대응 완료), `NOT_REQUIRED`(대응 불필요)로 구분한다.
- 최초 대응 상태는 `OPEN`이다. 정상으로 분석되면 `NOT_REQUIRED`로 자동 변경하며, 분석 대기·진행·실패만으로 `NOT_REQUIRED`로 변경하지 않는다.
- 자녀의 확인·완료는 명시적인 선택으로 기록한다. 상세 화면 조회만으로 확인 처리하지 않는다. 대응 완료는 가족이 조치를 마쳤다는 뜻이며 안전을 보증하지 않는다.
- 가족 확인의 발송 인정·부인·응답 만료는 별도 결과다. 해당 결과만으로 사건의 대응 상태를 완료로 변경하지 않는다.
- 모든 통화 사건을 저장하되, 자녀 알림은 검증된 위험·의심 결과가 있는 사건에 한정한다. 위험·의심에 해당하는 구체적인 분류값은 AI 결과 계약에서 정한다.
- 자녀 알림 대상 제한과 사건 목록·상세 조회 범위는 구분한다. 자녀 조회 1차는 6.0절의 공개 조건을 적용해 정상 통화를 숨긴다.
- 재분석에 따른 대응 상태 변경과 재알림 조건은 후속 재분석 기능을 설계할 때 정한다.

## 7. 비기능 요구사항

- 보안: 가족별 조회 권한, 원본 미노출, 최소 정보 보관.
- 로깅/모니터링: 사건 생성·상태 변경·처리 실패를 추적한다.

- [ ] Given 정상으로 분석된 통화, When 분석 결과를 반영하면, Then 대응 상태는 `NOT_REQUIRED`이며 자녀 알림은 생성하지 않는다.
- [ ] Given 위험·의심으로 분석된 통화, When 검증된 분석 결과를 반영하면, Then 해당 사건을 자녀 알림 대상으로 삼는다.
- [ ] Given 분석 대기·진행 또는 실패 상태의 통화, When 검증된 위험·의심 결과가 없으면, Then 자녀 위험 알림을 생성하지 않으며 대응 불필요로 처리하지 않는다.
- [ ] Given 자녀의 발송 인정·부인 또는 가족 확인 만료, When 확인 결과가 확정되면, Then 그 결과만으로 사건의 대응 상태를 완료로 변경하지 않는다.
